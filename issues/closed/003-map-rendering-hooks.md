# 003 — Map camera and rendering hooks

## Goal

Identify where independent eye views can be produced without running game simulation twice, with enough evidence to begin OpenXR integration. Roadmap stage: 1. Depends on #001 and benefits from #002.

## Tasks

- [x] Trace the game camera, full viewport-copy path, and main-world culling input at list construction and command execution. Numerically validating headset eye matrices and all culling consumers remains in #006.
- [x] Map the measured viewport-command and post-processing order, and associate phone and pause-map phases with their visible modes. Exact UI draw/pixel attribution and subtitles are tracked in #007.
- [x] Validate an opt-in two-view scene-command boundary with distinct camera snapshots after one observed game-process update. Independent visibility, render targets, and final pixels are tracked in #006.
- [x] Measure or log invocation order for relevant hooks in `source/fusiondxhook.ixx`, `source/dllmain.cpp`, `source/common.ixx`, `source/comvars.ixx`, and `source/postfx.ixx`.
- [x] Write a short design note with annotated hook points, unresolved risks, and a candidate boundary for per-eye scene rendering.

## Done when

The design note gives runtime evidence for a two-view scene-command boundary that can be used for the first OpenXR integration, shows one observed game-process update for two views, and explains which observed passes need per-eye versus headset-locked treatment. Record remaining defects and unresolved passes explicitly. An EndScene callback or an untested candidate boundary alone is not sufficient evidence of stereo feasibility.

- Source leads for culling: `source/experimental.ixx` has an opt-in reflection `AddToDrawList` hook and `RemoveBBoxCulling` patch; `source/fixes.ixx` has a commented-out `IsSphereVisible(grcViewport*, ...)` hook. - Ghidra 12.1.2 read-only decompilation of game version 1.2.0.59: source hook signatures resolved to `SceneToGBuffer::BuildRenderList` at `0x00d685f0`, `LightsToScreen::BuildRenderList` at `0x00d67a50`, and `DrawScene::BuildRenderList` at `0x00add200` (database image base `0x00400000`). The draw-scene function constructs `CSetCurrentViewportDC` from its phase viewport at offset `0xB0`; its constructor at `0x008dc0d0` copies viewport state via `0x005dc220` into a queued command. The command's vtable execution method at `0x008dde00` passes the copied viewport to `func_0x00430bf0`. The queue dispatcher and exact culling order are still unresolved. Decompiled output is local under ignored `build/` only.
- A `LightsToScreen::BuildRenderList` call at `0x00d6842b` reaches `0x00abd820`, which creates a generic command carrying `0x00ac1030` and box data. The callback reads the global current viewport's frustum plane fields before visibility tests. This identifies a viewport-dependent deferred-lighting culling path.
- Ghidra resolved the opt-in `RemoveBBoxCulling` pattern to `FUN_00ae67a0`, a visibility routine with several callers. Its `param_2[0xf] == 1` branch tests positions/radii against shared plane arrays written through `FUN_00928f20`. RTTI identifies the phase method `FUN_0092e2a0` feeding that cache as `CRenderPhaseCascadeShadows`. This establishes a shadow-camera dependency; it does not yet establish main-scene culling or timing.
- The `SceneToGBuffer` and `DrawScene` vtables identify setup methods at `0x00d68bd0` and `0x00a87df0`. Disassembly shows each copies a parent render context viewport (`parent + 0x10`) into two embedded phase viewports (`phase + 0xB0` and `phase + 0x4A0`); `BuildRenderList` is a separate slot-8 method. This moves the candidate stereo boundary upstream to the parent view setup; live sequencing and safe duplication remain unproven.
- The non-shadow branch of `FUN_00ae67a0` can reach `FUN_00a31c20`, which calls the same viewport sphere-test routine (`FUN_00431e40`) referenced by FusionFix's commented `IsSphereVisible` hook. The on-disk routine does not decompile cleanly, so main-scene timing and exact plane inputs still need runtime confirmation.

- 2026-10-01 viewport-command traces: an opt-in execution hook observed `CSetCurrentViewportDC` on the render thread, typically 33 times before each `postfx_begin` in steady free roam. A constructor/execute pairing trace then reached 30,000 events with 8,049 constructions and 8,018 executions; every execution paired to a preceding construction by command address. External RTTI tied each logged source viewport (`source - 0xB0`) to a phase object. In 216 measured post-processing intervals, viewport-command order was stable: pre/post-render and radar, tree imposters, eight warp shadows, mirror/water and other reflections, G-buffer, four lighting commands, then three main DrawScene commands. This is viewport-command order, not all draw calls or final UI pixels. Most command pairs were 15–16 ms apart; game-frame identity, main-world culling, and safe duplication remain unproven. The initial constructor signature did not match due to relocated bytes; a wildcarded version worked. Raw traces/mapping are ignored under `build/`; the working ASI was restored and tracing disabled.
- 2026-10-01 frame-ID trace: an opt-in Release build assigned a counter at each `game_process` callback and reached 30,000 events without crash. Of 7,550 viewport-command executions paired to a construction after initialization, 6,400 ran before the next game-process event and 1,150 afterward; none executed twice without reconstruction. This confirms cross-thread overlap and the need to carry eye state with queued work. It does not prove the whole scene can be built twice.
