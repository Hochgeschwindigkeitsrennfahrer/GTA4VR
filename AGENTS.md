# Working instructions for this fork

This repository is a FusionFix-based GTA IV VR project. Read `ROADMAP.md` before planning VR work. Preserve the user's existing changes, including the current `readme.md` edit. Do not edit the installed game as a substitute for making source changes in this repository.

Track work in the GitHub issue tracker at https://github.com/bordplate/GTA4VR/issues. Start from an existing open issue or create one before implementation. Record evidence as work proceeds; close an issue only when its acceptance conditions are met or it is explicitly canceled/superseded. Do not recreate the local `issues/` tracker. Historical three-digit issue IDs in technical notes predate the GitHub migration and are not GitHub issue numbers; use current GitHub URLs for active work.

## Scope and design

- Target the official GTA IV Complete Edition and single-player use. Track GTA IV, TLAD, and TBoGT behavior separately.
- Keep VR enabled by default with `[VR] DisableOpenXR=1` as the opt-out and retain a working flat-screen launch. A missing OpenXR runtime or headset must fail gracefully.
- The ASI is x86. Check the bitness of every native dependency, including any OpenXR loader or graphics bridge.
- Prefer a small VR module with clear ownership of OpenXR resources over scattering session state across unrelated FusionFix fixes.
- Separate game simulation, per-eye scene rendering, and headset submission. Do not call a duplicated frame VR merely because the headset displays it.
- Validate camera matrices, render order, depth, frame timing, and D3D9-to-OpenXR interop experimentally before committing to an architecture.
- Keep upstream fixes easy to merge. Avoid unrelated refactors and changes to installer behavior until needed by a milestone.
- For user-editable VR tuning, validate syntax/types and finite numeric values without arbitrary min/max limits. Retain only structural checks needed for valid operations (for example, a nonzero axis for normalization). Do not reject a whole profile merely because a tuning value exceeds a guessed useful range.

## Repository workflow

1. Inspect `git status` before work and leave unrelated edits untouched. Record baseline versions and exact repro steps for runtime bugs.
2. Use short branches and focused commits. Document observations, unknowns, and acceptance evidence against the relevant `ROADMAP.md` milestone.
3. Generate the Visual Studio solution with `premake5.bat` when needed. Build x86 Release for runtime and performance iterations. Do not also build Debug if only Release will be run; use Debug when its assertions, debugger behavior, or a Debug-specific problem is needed. Check `.github/workflows/msvc_x86.yml` when changing the build.
4. For local deployment, `premake5.lua` reads ignored `.env` with `GTAIV_DIR` pointing to the folder containing `GTAIV.exe`. It copies only the built ASI when the target plugin already exists. Back up that plugin and verify the target path before enabling deployment.
5. Per the user's testing preference, focus scoped VR camera/culling iterations on VR. Test flat-screen behavior when a change materially affects shared rendering, fallback or lifecycle, and before closing the issue; do not repeat a flat-screen launch for every guarded experiment. Add focused automated checks for deterministic math or lifecycle state; verify headset behavior manually with a recorded runtime/headset configuration.
6. Include in each change report: what changed, build/test results, game/runtime versions when relevant, observed frame-time data if performance is claimed, and remaining limitations.
7. To launch this Steam Complete Edition install for runtime tests, run `steam.exe -applaunch 12210` outside the restricted command sandbox or start `GTAIV/PlayGTAIV.exe` directly. Both routes have worked, and either can exit intermittently during startup. Verify that `GTAIV.exe` appears and remains responsive; `PlayGTAIV.exe` or Rockstar Launcher alone does not establish success. Do not launch a second copy while `GTAIV.exe` is running.
8. Iterate quickly on measured bottlenecks. Reuse existing comparable baselines instead of repeating before captures for every experiment. Recapture when scene/view, graphics settings, backend, runtime state, or relevant code changes invalidate the comparison, or when drift prevents a conclusion. Start with short omission/payoff tests of the largest costs before shader parity refinement or extensive validation. Repeat or broaden measurements only to answer a concrete unresolved question. Keep necessary controls and restore normal rendering after diagnostics.

## Development command bridge

- Prefer the local named-pipe bridge over UI automation for supported game commands. Enable `[DEVELOPMENT] EnableCommandBridge=1` in the installed ASI's INI for development; the distributed default remains off. Preserve the installed INI and ASI before deployment.
- Keep passive diagnostics off for ordinary gameplay: `DiagnosticLogging`, `DiagnosticCounters`, `DiagnosticObservationHooks` and `DiagnosticAutomaticCaptures` default to 0 under `[DEVELOPMENT]`. Enable only the controls needed for an investigation, restart to apply, and restore them afterward. Explicit profiling/capture commands remain available. Use `diagnostics-status` to distinguish disabled counters from inactive gameplay. `[VR] ShowFirstPersonBody=1` is the normal default, not a debug option. See `docs/vr-diagnostics.md`.
- Run `tools/game-command.ps1 status` to inspect the current game/OpenXR session and `tools/game-command.ps1 quit` to release OpenXR on the EndScene callback thread and request the game's normal window close. Use `-GameProcessId` when discovery is ambiguous. Verify that `GTAIV.exe` actually exits before deploying or launching another copy; command acceptance alone is not exit evidence.
- The user has authorized closing and relaunching the game for tests. Do not repeatedly ask them to launch or quit manually. The bridge does not save the game; do not add save-writing or arbitrary-execution commands without a specific user request. See `docs/development-command-bridge.md` for protocol and limits.
- The user also authorized reading, storing and restoring the player location for repeatable profiling. Per the 2026-10-07 correction, do not automatically teleport back after development relaunches; restore only when a test really requires the saved location. Use `tools/game-location.ps1 Capture/Restore -Path build/profiles/<label>-location.json`; the bounded native teleport runs on the simulation callback. Check completed operation/readback, allow streaming to settle, and inspect a fresh image before comparison. Only unpaused on-foot free roam is supported. Preserve the same episode/build; coordinates do not restore traffic, weather, time or headset orientation. Keep snapshots out of Git and leave saves untouched.
- Avoid Computer Use during game testing: the user reports significant performance overhead (2026-10-11). Prefer the command bridge, bounded process reads and explicit in-game captures. Use Computer Use only when a necessary UI task cannot be handled otherwise or the user requests it. Process responsiveness and RPC status alone do not prove a correct image; obtain visual acceptance from an explicit capture or the user's headset check.

## Ghidra project workflow

- Keep `[VR] ExperimentalStereoFrames=0` for continuous development headset rendering, as requested by the user. Do not time-limit manual headset checks to 600 frames. Values 1–600 remain useful for bounded diagnostics. With stereo ready, `tools/game-command.ps1 stereo-test` resets the experiment/capture without relaunching. Inspect `stereo` in `status` and fresh images; command acceptance alone is not rendering evidence.
- `[VR] MatchHeadsetRefresh=1` lets `xrWaitFrame` pace active stereo by skipping the ordinary gameplay limiter while OpenXR requests rendered eye images. The saved limiter resumes when VR stops or fails; loading, cutscene and minigame safety caps remain. Record `displayRefreshHz` separately from measured `submittedHz`; neither the setting nor the hardware query proves native FPS. Build and measure Release before performance claims.
- Verify the selected backend in `CSettings::d3d9cfgPath` (normally the installed game's `d3d9.cfg`): `[MAIN] API=0` is the supported system D3D9Ex bridge, `API=1` selects DXVK. This option is separate from the ASI INI. Back up the config before changing it for a test. DXVK cannot use the D3D11 shared-eye bridge. The #013 prototype requires `[VR] ExperimentalVulkanBridge=1` and, on this SteamVR installation, `VulkanOpenVRBootstrap` pointing to the existing absolute x86 `bin/win32/openvr_api.dll` path. Ship the tested Vulkan bridge enabled with automatic SteamVR discovery; keep the path override empty; game compatibility and performance acceptance are pending. See `docs/vulkan-openxr-feasibility.md`.
- Synchronize every Vulkan queue user through DXVK's interop queue lock: our submissions and OpenXR `xrBeginFrame`, `xrEndFrame`, `xrAcquireSwapchainImage`, and `xrReleaseSwapchainImage`. Do not call D3D9 or nest the lock inside a locked callback. `xrWaitFrame` and `xrWaitSwapchainImage` do not need that queue lock. GPU completion is a separate requirement before image release. `[DEVELOPMENT] VulkanDebugMode=hang` enables process-local DXVK hang diagnostics before device creation; remove it for performance captures. Preserve any existing `dxvk.conf` before compatibility experiments and verify the effective settings in the fresh DXVK log.

- Use the Ghidra MCP for game-binary analysis. At the start of a session, call `list_instances`, connect to `GTAIV` with `connect_instance` if needed, then call `list_open_programs`; confirm `/GTAIV.exe` is the intended program before editing. Pass `program: "GTAIV.exe"` on program-specific calls, especially if more than one program is open. The tested import is 32-bit x86 with Ghidra image base `0x00400000`.
- Search existing functions, names, bookmarks, comments, and types before reanalyzing an address. Use MCP disassembly, decompilation, cross-references, and runtime evidence together. A decompiler guess alone is not proof of behavior. Record the game version and distinguish Ghidra addresses from relocated runtime addresses; obtain the live module base for each run instead of assuming a fixed offset.
- Persist findings in the Ghidra project as the analysis proceeds. Rename a function when its role is supported by code and observations; add comments or bookmarks with the issue ID, evidence, and remaining uncertainty. Apply verified prototypes, types, and variable names when they improve later analysis. Use a bookmark or comment for a tentative interpretation rather than a confident symbol or type.
- Preview edits with `dry_run` when the MCP tool supports it. Read back the changed function or annotation, then call `save_program`. Keep `docs/` and the GitHub issue updated with the address, conclusion, and evidence so repository collaborators can understand project-only annotations. The Ghidra project is outside Git; do not copy its database or imported game binary into this repository.
- Avoid destructive reanalysis, flow repair, rebasing, or bulk renaming without a specific finding that requires it. If the MCP is unavailable, record the evidence in the issue and state that the Ghidra project was not updated; do not imply a local note was saved there.

## Safety and distribution

- Never commit game files, proprietary SDK binaries, headset logs, `.env`, or local build output. The user authorizes bundling the tested Animated Weapons archive under third_party/animated-weapons with its credited redistribution permissions and original notices; this exception does not authorize arbitrary game assets.
- Do not modify player saves or change Steam/game files outside an explicit deployment or test step. Keep backups for any overwritten ASI or config.
- Preserve the GPL-3.0 license and required notices. Keep the project single-player; do not add multiplayer or online hooks.
- Avoid presenting unverified VR support, comfort, compatibility, or performance as complete.
