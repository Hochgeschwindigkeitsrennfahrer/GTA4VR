## Scene-dependent command-buffer overflow (#029, 2026-10-02)

The reproducible frozen view in CE1.2.0.59 PID16412 (live image base00800000) set one overflow byte in the native command manager at Ghidra `01175C58`; turning away cleared both bytes and headset submissions resumed in the same process. A bounded thread snapshot detached successfully and found the render thread waiting for native work at `008D8C03`, while simulation continued. This distinguishes discarded command streams from an established GPU/shader deadlock.

`008DEB60` allocates two buffers of `0x202710` bytes: 2 MiB plus 10,000 bytes of padding. `008DCAD0`, `008DC3A0` and `008DC7E0` check the 2 MiB producer limit, reset the cursor and mark the write buffer overflowed. `008DEAB0` enforces the matching reader bound; `008DE060` skips an overflowed buffer. Manager offsets: buffers +0/+4, overflow bytes +8/+9, read/write slots +10/+14, read/write cursors +18/+1C (hex). Live instructions and frozen/working counter samples support this interpretation; no individual asset has been identified as defective.

The guarded stereo initialization increases both native allocations and all four matching bounds to 8 MiB, keeping padding, slot switching, native allocator and release ownership. This adds 12 MiB across both buffers. Status reports capacity, the observed post-build peak and overflowed builds; the peak is sampled, not an exact allocator high-water mark. `tools/read-render-command-pool.ps1 -GameProcessId <PID>` independently reads the verified live capacity, slot counters and overflow flags without attaching a debugger or changing game fields. Its snapshot is non-atomic. Scene-route validation remains pending. `Issue029CommandBufferOverflow` was applied, read back and saved in Ghidra.

The OpenXR cached-view and gameplay-pacing gates also expire after250ms without a fresh pose, matching the existing focused-gameplay gate. Ordinary scene construction and the saved limiter then resume until fresh views return. This fallback allowed headset input during the observed interruption; it does not itself establish a fix for command-buffer exhaustion.

## Model-reference lifetime overflow (#029, 2026-10-02)

CE1.2.0.59 hardware write watch in PID6216 (live base00800000) caught native `0094203A` writing a model ID into input-device object1E0E4EC0 during DrawScene command construction. The ushort list index was4008, already beyond native capacity4000 (16,384). These repeated16-bit values are **model IDs**, not GPU mesh indices: `00AC1B30` passes entity+2E, and `00942000` increments the model-info reference at+44 before appending the ID. Ghidra now names it `RetainQueuedModelReference`.

Manager `011D4EC8` owns four queued lifetime lists: active slot+2040, data+204C+slot*8, count+2050, capacity+2052. `009422B0` allocates8000 bytes per list; the append does not check capacity. `009424E0` releases the recorded references after command execution and resets the count. This explains a captured buffer overwrite and later invalid input-device vtables; additional faults still require route validation.

The source correction enlarges the native allocation/capacity to1FFFE bytes/FFFF entries before initialization, preserving native allocation and release ownership. While stereo is ready, it adds one new hold per distinct nonnegative signed-short model ID per queued list, retaining any preexisting holds with their original multiplicity. It resets tracking on native list reuse and includes preexisting IDs before skipping duplicates. Model-reference peak and skipped duplicates are exposed through stereo status. The production tracker in `source/includes/vrmodelrefs.hpp` passed x86 release-balance tests covering repeated draws, queue recycling, preexisting holds and fallback/resume. Final x86 Debug/Release builds passed. Release9AFFF349... PID29664 confirms native capacity65535, increasing continuous stereo and valid input-device pointers. Repeated apartment/car route and flat-screen fallback verification remain pending; #014/#029 stay open.

Evidence from GTA IV Complete Edition 1.2.0.59, FusionFix-based x86 Release, D3D9 borderless, 2026-10-01. The two-view command boundary was exercised for one frame; complete stereo images and headset rendering remain unproven. Raw game traces remain local and are not committed.

## Observed hook sequence

### Issue 014: first-person interior visibility (2026-10-02)

On CE 1.2.0.59, changing the main viewport's six clip planes did not stop apartment furniture disappearing when the headset turned behind the ordinary mouse camera. Correcting shared-parent sphere queries also failed that reproduction.

The interior path at `0x00A11280` invokes `0x00A111B0`/`0x00A10470` before it can return without rasterizing the main spatial grid. `0x00A11500` builds a shared four-plane volume from the ordinary camera; `0x00A10470` tests interior objects through `0x00A0FCF0` before their phase sphere test. The volume test is thiscall `(center*, radius)`, returns true for outside, and cleans eight stack bytes. The initial assumption that this volume belonged at scene `+0x50` did not cover the interior calls.

The first-person correction scopes this query by the active main scene phase (`0x012FB1B8` in Ghidra), using the prepared conservative eye union. Other phases retain their original volume tests. Release `D2CE656C57BED85278AE04EED66147E899535D1A2F64F2A8C3B78A9D21B88B49`, live PID 12028, corrected 21497 stale-volume rejections by frame 840. The user then confirmed TV, bed and rear furniture remain visible on headset rotation without mouse movement or visible popping. SteamVR/OpenXR 2.17.10, continuous first-person stereo, system D3D9Ex; room-scale body movement remains unimplemented. This accepts the apartment reproduction, not all-scene visibility or a performance improvement. `Issue014CameraVolume` was read back and saved in the Ghidra project.

The separate grid hook at `0x00D62DC0` preserves cell callbacks and phase bits while covering the same eye union for the main phase. It was unused in this indoor reproduction; bounded observations and read-only RTTI identified the observed grid calls as WarpShadow/Reflection. Outdoor grid coverage remains unverified.

### Issue 014: candidate collision motion path (2026-10-02)

CE `CPedMoveBlendOnFoot` is constructed at `0x00CBCA00` and stored by `0x009E8C60` at ped `+0xA80`. Its vtable is `0x00ED90C4`, with the owning ped at component `+0x24`. A read-only live sample in PID 25852 confirmed both pointers. The inline ped `+0xBB0` component is `CIkManager` (RTTI `0x01050CD8`), so its update at `0x00C9F370` must not be mistaken for a walking motor.

Move-blend virtual `+0x10` at `0x00CC3480` takes `(outputVector*, float timestep)` with thiscall and `ret 8`, returns the output pointer, subtracts current physics velocity from animation/support motion, and bounds the vector using the timestep. The unchanged-output diagnostic observed local-player calls from `0x009E3337` at timestep 0.006667 while standing. Assembly in its caller `0x009E32D0` multiplies the vector by a physics archetype scalar and inverse timestep, then calls `0x00B23610` to dispatch collider virtual `+0x84`. Static `0x007555E0` adds into the force accumulator at collider `+0x150/+0x154/+0x158`. This is a candidate delta-velocity-to-force path; normal walking coverage and collision-safe room-scale injection remain unverified. `Issue014IKManager`, `Issue014MoveBlend` and `Issue014MotionForce` were read back and saved in Ghidra. No body writes are implemented.

### Issue 014: headset-relative keyboard/gamepad direction (2026-10-02)

Camera helper `0x009B6370` takes thiscall `(camera*, ped*, bool)`, returns an x87 float and uses `ret 8`. Ordinary axis handlers `0x00A6DA70`, `0x00A741D0` and `0x00A746D0` use its yaw as the reference for a planar input angle. `ExperimentalHeadRelativeMovement` replaces this reference for the local player with the first-person headset heading, `atan2(cameraBack.x, -cameraBack.y)`. It preserves the input magnitude and the original animation/collision pipeline. Head pitch/roll do not add vertical motion; a near-vertical gaze retains the preceding horizontal reference. Focus, pose freshness, recenter and first-person fallback gate the snapshot.

The first inline-hook prototype stalled loading before any movement override activated; disabling that hook restored a successful VR launch on the same ASI. The corrected callback compares against the ped owner published with a valid on-foot camera, avoiding player lookup during loading. Corrected Release `61A22AFFCCD02E1DC1C67B1F35DD909484E4B574B2D152AA025CC05140B6DEDD` reached gameplay in PID 7600 with increasing local yaw overrides and a fresh coherent outdoor image. The user then confirmed head-relative forward/back/left/right and level movement when looking up/down. This accepts that input-reference test, not all devices/special actions. `Issue014HeadRelativeMovement` records the verified ABI and evidence in Ghidra; room-scale body movement remains separate unfinished work.

## Live viewport and phase observations

With the known working ASI installed and the game in the user's free-roam save, `tools/inspect-viewport.ps1` read the process externally using `ReadProcessMemory` only. It found the live `pCurrentViewport` signature at `0x00F80BF8` and its pointer global at `0x0234583C`. The pointer is transient during rendering; polling it captured multiple viewport objects. These addresses are from this process/version and must be resolved again on another run.

Of 40 viewport samples, 21 had FOV 45°, aspect 1.78, near/far 0.05/1500, camera position about `(896.77, -505.29, 16.12)`, projection diagonal about `(1.36, 2.41)`, and a populated first frustum plane. Five more shared the XY position with negative Z. Fourteen had FOV 60°, a camera near the origin, aspect 0, and near/far 1/1000. Another sample had FOV 14.25° and near/far 448/576. There were 32 distinct viewport addresses among the first 40 samples. The FOV 45° group is consistent with the active free-roam camera, but these groups have **not** been paired reliably with named render phases. The different values show why sampling `pCurrentViewport` at an arbitrary time cannot be treated as sampling the main eye camera.

The same read-only probe found the live `CRenderPhase::sm_pCurrent` pointer global at `0x01E4B1B8` and decoded object types through RTTI. A three-second poll saw 1,831 nonzero reads and 23 distinct phase objects, including `CRenderPhaseDeferredLighting_SceneToGBuffer`, `CRenderPhaseDeferredLighting_LightsToScreen`, `CRenderPhaseDrawScene`, `CRenderPhaseRadar`, `CRenderPhaseWaterReflection`, `CRenderPhaseReflection`, `CRenderPhaseCascadeShadows`, and `CRenderPhasePostRenderViewport`. This confirms that radar, reflections, shadows, and the world scene have separate live phase objects. The probe samples a global pointer across threads, so its transition list is **not** a reliable per-frame draw order or evidence of which phase owns a sampled viewport.

FusionFix already reads `*CRenderPhase::sm_pCurrent + 0x128` as camera Z in `source/fixes.ixx:796`. Since `grcViewport::mCameraMatrix[3][2]` is at offset `0x78`, this implies a phase-owned viewport beginning at phase offset `0xB0`. Reading that candidate field externally yielded coherent values: `SceneToGBuffer`, `LightsToScreen`, and `DrawScene` each held approximately `(896.4, -505.3, 15.9)`, FOV 45°, near/far 0.05/1500; `WaterReflection` held the same XY and opposite Z; `Radar` held an origin camera and FOV 60°. This is stronger evidence that the scene phase objects carry their own view state. The phase-owned viewport's matrix update point and the culling code that consumes it still need tracing.

With the user holding the in-game phone overlay open during free roam, a six-second phase poll saw 145 `CRenderPhaseScript2d` samples and seven `CRenderPhasePhoneModel` samples. Neither type appeared in the earlier free-roam polls. World scene, lighting, reflections, shadows, draw scene, and radar continued to appear. ## Candidate stereo boundary

The first OpenXR renderer can start from the measured `FUN_008f7f00` list boundary. Run `CGameProcessHook` and `FUN_008f7820` once; capture the world parent and phase viewports; build the first world command list; set the G-buffer, deferred-lighting, and DrawScene phase viewports from the runtime's second eye pose/FOV; build the second list; then restore phase state. The command object copies each viewport before render-thread execution, so each queued pass retains its camera even when the game/list thread advances. The one-frame stress test established this sequence with two distinct valid cameras and one observed game-process callback.

This is a **command-generation boundary**, with known work still required before a headset image: route each pass to its eye's render target, use a conservative shared visibility set or independent traversal state, generate complete eye-consistent matrices/frusta, and handle deferred lighting, shadows/reflections, post-processing, and UI. Repeating `FUN_008f7820` after list construction crashed even with the same camera, so the first implementation must not do that. The second-view stress camera was a radar viewport, not a headset pose; no pixel-level stereo correctness was asserted. These requirements are tracked in [#006](../issues/open/006-eye-visibility-and-targets.md), with UI attribution in [#007](../issues/closed/007-ui-composition-order.md).
