# GTA IV render pipeline notes (issue 003)

Evidence from GTA IV Complete Edition 1.2.0.59, FusionFix-based x86 Release, D3D9 borderless, 2026-10-01. The two-view command boundary was exercised for one frame; complete stereo images and headset rendering remain unproven. Raw game traces remain local and are not committed.

The Ghidra 12.1.2 database for `GTAIV.exe` uses image base `0x00400000`. Addresses below are database addresses; live addresses differ because the running image is relocated. GhidraMCP's local REST plugin was used read-only for the decompilation observations.

## Observed hook sequence

An opt-in Release trace recorded 6,000 events over 22.1 seconds. Its `game_init` event was sequence 530. In steady state, 681 frames showed the following recurring sequence. The two rows run on different threads, so events sharing a millisecond cannot be assigned a strict cross-thread order:

| Thread | Repeating events | Source |
| --- | --- | --- |
| Game/list thread 15672 | `game_process` → `scene_to_gbuffer_list` → `lights_to_screen_list` → `draw_scene_list` | `source/dllmain.cpp` and `source/comvars.ixx` |
| Render thread 15488 | `postfx_draw_call` → `postfx_begin` → `postfx_end` → `end_scene` | `source/postfx.ixx` and `source/dllmain.cpp` |

The trace counted 682 `game_process`, `scene_to_gbuffer_list`, and `lights_to_screen_list` events; 681 `draw_scene_list` and post-processing triplets; and 1,228 `end_scene` events because the callback also runs during startup. This demonstrates a list-building path separate from the post-processing/present path. It does **not** establish which list is consumed by which render frame, or that a list can be replayed with another camera.

A second opt-in, event-only Release trace on 2026-10-01 added entry/exit events for the `SceneToGBuffer` and `DrawScene` viewport setup methods identified in Ghidra. It reached the 6,000-event cap without a crash; `game_init` was sequence 896. On game/list thread 2228, **all 231 complete `game_process` segments** had this order:

`game_process` → 3 × (`draw_setup_begin` → `draw_setup_end`) → `scene_setup_begin` → `scene_setup_end` → 3 × (`draw_setup_begin` → `draw_setup_end`) → `scene_to_gbuffer_list` → `lights_to_screen_list` → `draw_scene_list`.

The final segment was truncated by the event cap. The render thread was 24052. This verifies that the sampled setup calls completed before the list callbacks on the same thread and that simulation was observed once per segment. The six calls to the shared `DrawScene` setup routine per segment indicate multiple instances/passes. It does not prove that re-entering the phase setup/list path is safe. After the run, the trace marker was removed, the backed-up Release ASI was restored with matching hash, and the game relaunched responsively.

A third opt-in trace logged only the setup object's address, without dereferencing it in the ASI. It reached the 30,000-event cap without a crash. All 1,325 complete game/list-thread segments had the same setup/list shape as above and the same six setup object addresses in this order. A concurrent read-only external probe identified their RTTI types and candidate embedded camera values:

| Setup order | Runtime object in that run | RTTI phase type | Role indicated by type/viewport |
| --- | --- | --- | --- |
| 1 | `0x119F9C10` | `CRenderPhaseWaterSurface` | Water pass, world camera |
| 2 | `0x119FC240` | `CRenderPhaseCloudGeneration` | Cloud pass, world camera |
| 3 | `0x119FCB90` | `CRenderPhaseRainUpdate` | Rain pass, world camera |
| Between 3 and 4 | `0x119FDE40` | `CRenderPhaseDeferredLighting_SceneToGBuffer` | Scene setup, world camera |
| 4 | `0x119FE7A0` | `CRenderPhaseDeferredLighting_LightsToScreen` | Lighting setup, world camera |
| 5 | `0x119FF100` | `CRenderPhaseDrawScene` | Main draw-scene setup, world camera |
| 6 | `0x0DE387C0` | `CRenderPhaseRadar` | Radar setup, origin camera |

The addresses are process-local and only identify objects in that run. This establishes the main draw-scene setup's place in the measured sequence and shows that the same setup routine is inherited by several phases. It does not establish a safe way to skip, duplicate, or replay any one of them. The working Release ASI was restored again with a matching backup hash and GTA IV relaunched responsively.

A fourth opt-in Release trace recorded both the setup object and its `parent` argument, without dereferencing either pointer inside the ASI. It reached the 30,000-event cap without a crash. There were 1,325 `game_process` events and 1,324 complete sets of the G-buffer, lighting, and draw-scene list callbacks. In this run, all 1,325 `WaterSurface`, `CloudGeneration`, `RainUpdate`, and `SceneToGBuffer` setup calls used parent `0x117F7BB0`; 1,324 `LightsToScreen` and main `DrawScene` setups used that same parent. The 1,329 observed radar setup calls used a different parent, `0x117F8130` (including startup and the truncated final segment). These are process-local addresses. The raw CSV is ignored under `build/issue003-parent-trace.csv`.

An external read-only probe of `parent + 0x10` while this run was in free roam found the shared world parent at camera `(891.77, -496.50, 20.27)`, FOV 45°, aspect 1.777778, near/far 0.05/1500, with populated projection and first frustum-plane fields. `SceneToGBuffer` and `DrawScene` phase viewports at offsets `0xB0` and `0x4A0` matched that camera in a later sample. The radar parent had a different top-down camera `(892.44, -499.80, 69.43)`, aspect 1, near/far 0.05/800. Radar's phase viewport at `0x4A0` matched it, while its `0xB0` viewport held an origin/default view. Thus, the parent pointer identifies separate world and radar view contexts, but the active embedded viewport cannot be inferred from the phase type alone. Because the parent and phase reads were asynchronous, this is not a per-command execution pairing.

A fifth opt-in trace hooked the `CSetCurrentViewportDC` virtual execution method (`FUN_008dde00`). It logged 11,050 execution entry/exit pairs across 321 `game_process` events before reaching the 30,000-event cap. Every execution callback ran on the render thread in that run; setup and list callbacks ran on the game/list thread. After `game_init`, 309 of 320 intervals ending at `postfx_begin` contained 33 viewport-command executions, ten contained 34, and one contained 29. This shows a stable command stream before post-processing on the render thread. It does not assign each command to a named phase or prove which game/list frame it consumes. The ASI was restored afterward.

A sixth opt-in trace paired `CSetCurrentViewportDC` construction (`FUN_008dc0d0`) with execution by command-object address. The first constructor signature failed to match at runtime because it included relocated address bytes; a wildcarded signature compiled and ran. The successful run reached the 30,000-event cap with 8,049 constructions and 8,018 execution entry/exit pairs. Every recorded execution had an earlier construction of the same command object. The constructor logged the source viewport pointer without dereferencing it; an external read-only RTTI probe associated `source - 0xB0` with a live phase object. The paired commands included `WarpShadow`, reflections, G-buffer, lighting, `DrawScene`, radar, and pre/post-render viewport phases. Most measured construction-to-execution delays were 15–16 ms (7,330 of 8,018 pairs), but the trace does not yet identify a game frame ID for each command. Raw CSV and phase mapping remain ignored under `build/`.

In that final trace, 216 intervals ending at `postfx_begin` had the same **viewport-command** phase sequence: post/pre-render viewport and radar commands; tree imposters; eight warp-shadow commands; mirror and water reflection; four reflection and four interior-reflection commands; pre-render viewport; one G-buffer command; four lighting commands; and three `DrawScene` commands. Ten intervals added a `Script2d` viewport command at the front. These are calls that change the current viewport, not a complete draw-call or final-pixel order. `Script2d` in this trace does not establish which overlay it drew. The trace ended at the event cap, so the final interval may be incomplete.

A seventh opt-in run added a monotonically increasing ID at each `game_process` callback, before the original game-process routine. It again reached 30,000 events without a crash. In the complete sampled part after `game_init`, 229 game-process IDs each had one G-buffer, lighting, and draw-scene list callback. Of 7,550 viewport-command executions paired to a recorded construction after initialization, 6,400 ran while the construction frame ID was still current and 1,150 ran after the next `game_process` event incremented the ID. No sampled command executed twice without reconstruction. This confirms that game/list construction and render-thread execution overlap across the frame boundary; a render-thread read of the current game camera is not necessarily the camera used to construct that command. The ID is a trace counter, not an engine-provided frame token. The 30,000-event cap truncated the last frame. Raw CSV stays ignored under `build/` and the backed-up Release ASI was restored.

An eighth opt-in run sampled one call in every 1,024 to Ghidra `FUN_00ae67a0`, FusionFix's `RemoveBBoxCulling` lead. Its first launch exited with `0xc0000005` before a new trace file was created, so that attempt does not identify the faulting hook; a Steam relaunch of the same installed build reached the 30,000-event cap responsively. Sixty-nine sampled calls had five phase-object pointers. Read-only RTTI identified 13 calls with the live `CRenderPhaseDeferredLighting_SceneToGBuffer` object, plus `WarpShadow`, `Reflection`, and `InteriorReflection` objects. All 13 sampled G-buffer-phase calls fell after its setup and before the `scene_to_gbuffer_list` callback on the game/list thread in their respective trace-counter frames. An external read found the G-buffer phase's mode field at `+0x3C` equal to 2, so these calls take the non-shadow branch of `FUN_00ae67a0`. This is a sampled timing observation, not a total culling-call count.

Disassembly of that non-shadow branch calls `FUN_00a31c20` with the entity in ECX and the phase as a stack argument. `FUN_00a31c20` obtains the entity sphere center/radius through virtual methods, then loads ECX with `phase + 0xB0` immediately before calling `FUN_00431e40`, the viewport sphere-visibility routine referenced by FusionFix's commented hook. This establishes that the main G-buffer phase's embedded `grcViewport` at `+0xB0` is an input to this world-entity culling path before list construction. Other culling mechanisms may also apply; the routine's on-disk body still does not decompile reliably. The backed-up ASI was restored and tracing disabled after the run.

Caller-address logging of the setup hooks identified Ghidra `FUN_00b008c0` as a loop that calls virtual setup slot `+0x10` for four shared world phase objects, including `SceneToGBuffer`. The main `DrawScene` setup reaches the shared method through `FUN_00ade600`; radar uses `FUN_00e4e200`. Following callers upward found render setup routine `FUN_008f7820` and the later list-building routine `FUN_008f7f00`. An early static caller inspection found both in `FUN_005c2060`; later live traces showed that caller is a startup path, while steady free roam uses the code at `0x005c2b0f` and `0x005c2bf5` for these calls. An opt-in trace observed one entry/exit of each routine, in that order, for 203 complete game-process frames; G-buffer, lighting, and DrawScene list callbacks occurred inside `FUN_008f7f00`.

A one-frame, opt-in experiment invoked the original `FUN_008f7f00` a second time after its normal return in trace-counter frame 30, leaving the camera unchanged. The run stayed responsive through the 30,000-event cap. Frame 30 had one `game_process` and one `FUN_008f7820` call, but two G-buffer, lighting, and DrawScene list callbacks. It constructed 66 viewport commands, and all 66 were observed executing on the render thread; adjacent steady frames constructed/executed 33 each. This proves that this build can repeat list construction and command execution for a single frame without repeating the observed game-process callback. It does **not** prove two distinct eye views, correct culling on the second pass, independent render targets, or side-effect-free duplication. Raw evidence remains in ignored `build/issue003-duplicate-build-trace.csv`. The duplicate marker was removed and the working Release ASI restored with matching hash.

The next experiment tried calling `FUN_008f7820` again from inside the `FUN_008f7f00` hook after the first list pass. It exited at the second setup even with the unchanged world camera. Repeating that setup at this advanced point in the render graph is unsafe; the failure does not prove setup can never be repeated at an earlier scheduler boundary. A separate hook on `FUN_005c2060` showed that function runs during startup only, while live free-roam return addresses for setup/list construction were `0x005c2b14` and `0x005c2bfa` in the Ghidra image. These lie in a larger, incompletely analyzed steady-state scheduler function. The disassembly at `0x005c2b0f` calls `FUN_008f7820`; `0x005c2bf5` calls `FUN_008f7f00`. This corrects the earlier attribution of the free-roam owner to `FUN_005c2060`. The failed traces are ignored under `build/` and were never left installed.

A one-frame **two-view command experiment** kept setup and game processing single, then copied a complete, valid second `grcViewport` into the G-buffer, deferred-lighting, and main DrawScene phase viewports (`+0xB0` and `+0x4A0`) before calling `FUN_008f7f00` a second time. The second viewport came from the radar parent solely as a distinct-camera stress input; its top-down pose and projection are not headset eye views. In trace-counter frame 30 there was one `game_process`, one `FUN_008f7820`, two list callbacks for each of the three world phases, and 66 constructed viewport commands. G-buffer command snapshots for the first and second passes held cameras `(891.77,-496.50,20.27)` and `(892.44,-499.80,69.43)` respectively. A main DrawScene command from each pass held the same corresponding camera. All four tagged commands executed on the render thread with those copied camera values, although two executions occurred after the next `game_process` callback. GTA IV remained responsive through the trace cap. The phase viewports were restored immediately after the second list pass; the installed ASI was restored from the working backup and the markers removed. Raw evidence: ignored `build/issue003-stereo-boundary-trace.csv`.

The two-view test proves a repeatable **list/queued-command boundary**, not a complete stereo image. Main G-buffer visibility ran once between setup and the first list pass. None of the sampled `FUN_00ae67a0` calls repeated for the second view. Static analysis of `FUN_00a10140` shows an entity stamp check (`entity + 0x3C` versus `phase + 0x38`) that can suppress repeated traversal with the same phase/frame ID. The first OpenXR renderer therefore needs conservative visibility covering both nearby eyes, or truly separate per-eye traversal state; simply replaying the list builder will reuse visibility decisions. The test also did not route the two command streams to separate render targets, verify pixels, or characterize post-processing and UI. Those are explicit integration tasks rather than claims of working VR.

The diagnostic `source/vrtrace.ixx` uses a marker file and records event names only. A later attempt to sample viewport matrices crashed before a game window appeared (`0xc0000005`), twice. The known working Release ASI was restored and verified. Do not use that failed camera-sampling variant as evidence about viewport validity; no matrix sample was captured.

## Live viewport and phase observations

With the known working ASI installed and the game in the user's free-roam save, `tools/inspect-viewport.ps1` read the process externally using `ReadProcessMemory` only. It found the live `pCurrentViewport` signature at `0x00F80BF8` and its pointer global at `0x0234583C`. The pointer is transient during rendering; polling it captured multiple viewport objects. These addresses are from this process/version and must be resolved again on another run.

Of 40 viewport samples, 21 had FOV 45°, aspect 1.78, near/far 0.05/1500, camera position about `(896.77, -505.29, 16.12)`, projection diagonal about `(1.36, 2.41)`, and a populated first frustum plane. Five more shared the XY position with negative Z. Fourteen had FOV 60°, a camera near the origin, aspect 0, and near/far 1/1000. Another sample had FOV 14.25° and near/far 448/576. There were 32 distinct viewport addresses among the first 40 samples. The FOV 45° group is consistent with the active free-roam camera, but these groups have **not** been paired reliably with named render phases. The different values show why sampling `pCurrentViewport` at an arbitrary time cannot be treated as sampling the main eye camera.

The same read-only probe found the live `CRenderPhase::sm_pCurrent` pointer global at `0x01E4B1B8` and decoded object types through RTTI. A three-second poll saw 1,831 nonzero reads and 23 distinct phase objects, including `CRenderPhaseDeferredLighting_SceneToGBuffer`, `CRenderPhaseDeferredLighting_LightsToScreen`, `CRenderPhaseDrawScene`, `CRenderPhaseRadar`, `CRenderPhaseWaterReflection`, `CRenderPhaseReflection`, `CRenderPhaseCascadeShadows`, and `CRenderPhasePostRenderViewport`. This confirms that radar, reflections, shadows, and the world scene have separate live phase objects. The probe samples a global pointer across threads, so its transition list is **not** a reliable per-frame draw order or evidence of which phase owns a sampled viewport.

FusionFix already reads `*CRenderPhase::sm_pCurrent + 0x128` as camera Z in `source/fixes.ixx:796`. Since `grcViewport::mCameraMatrix[3][2]` is at offset `0x78`, this implies a phase-owned viewport beginning at phase offset `0xB0`. Reading that candidate field externally yielded coherent values: `SceneToGBuffer`, `LightsToScreen`, and `DrawScene` each held approximately `(896.4, -505.3, 15.9)`, FOV 45°, near/far 0.05/1500; `WaterReflection` held the same XY and opposite Z; `Radar` held an origin camera and FOV 60°. This is stronger evidence that the scene phase objects carry their own view state. The phase-owned viewport's matrix update point and the culling code that consumes it still need tracing.

With the user holding the in-game phone overlay open during free roam, a six-second phase poll saw 145 `CRenderPhaseScript2d` samples and seven `CRenderPhasePhoneModel` samples. Neither type appeared in the earlier free-roam polls. World scene, lighting, reflections, shadows, draw scene, and radar continued to appear. The phone model's candidate embedded viewport had an origin camera and FOV 70°, distinct from the world camera. This supports treating the phone model and phone UI as separate from the world view, but the asynchronous poll does not prove their drawing order or which pixels `Script2d` produces.

With the user holding the pause-menu map open, a six-second poll saw 11 `CRenderPhaseFrontEnd` samples; that phase had an origin camera and FOV 60°. It was absent from the prior free-roam and phone samples. The world scene, lighting, reflections, shadows, draw scene, and radar were still sampled, so opening the map did not make those phase objects disappear. This associates `FrontEnd` with the pause UI, but does not show which phase produces the map pixels or whether paused world passes actually draw to the final frame.

## Candidate stereo boundary

The first OpenXR renderer can start from the measured `FUN_008f7f00` list boundary. Run `CGameProcessHook` and `FUN_008f7820` once; capture the world parent and phase viewports; build the first world command list; set the G-buffer, deferred-lighting, and DrawScene phase viewports from the runtime's second eye pose/FOV; build the second list; then restore phase state. The command object copies each viewport before render-thread execution, so each queued pass retains its camera even when the game/list thread advances. The one-frame stress test established this sequence with two distinct valid cameras and one observed game-process callback.

This is a **command-generation boundary**, with known work still required before a headset image: route each pass to its eye's render target, use a conservative shared visibility set or independent traversal state, generate complete eye-consistent matrices/frusta, and handle deferred lighting, shadows/reflections, post-processing, and UI. Repeating `FUN_008f7820` after list construction crashed even with the same camera, so the first implementation must not do that. The second-view stress camera was a radar viewport, not a headset pose; no pixel-level stereo correctness was asserted. These requirements are tracked in [#006](../issues/open/006-eye-visibility-and-targets.md), with UI attribution in [#007](../issues/open/007-ui-composition-order.md).
